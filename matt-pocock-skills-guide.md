# Гайд: как строить продукт с помощью скиллов Мэтта Покока

Собрано по итогам разговора — от знакомства со скиллами до алгоритма разработки полноценного мультиплатформенного продукта. Сохранено, чтобы возвращаться и не забывать.

---

## 0. Что это вообще такое

Репозиторий: `github.com/mattpocock/skills` — набор из 24 продвигаемых скиллов (agent skills) для Claude Code, написанных Мэттом Пококом.

**Философия:** это не готовый процесс типа GSD/BMAD/Spec-Kit, которые отбирают у разработчика контроль. Это набор маленьких, независимых инструментов поверх реальных инженерных практик — TDD (красный-зелёный-рефакторинг), DDD (единый словарь терминов), смёллы кода по Фаулеру.

**Установка:**
- Как плагин Claude Code: `claude plugins install mattpocock-skills` (управляемый комплект, обновляется сам)
- Через `npx skills@latest add mattpocock/skills` (файлы копируются в проект, можно редактировать)

**Роутер по скиллам:** `/ask-matt` — если забыли, какой скилл когда использовать, спросите его.

**Отдельно от Покока:** на компьютере уже установлен скилл **`impeccable`** — это НЕ часть репозитория Покока, отдельный автор, отвечает за визуальный дизайн (см. раздел 5).

## 1. Карта скиллов Покока (кратко)

### Основной поток «идея → релиз» (7 шагов)

| Шаг | Команда | Что делает |
|---|---|---|
| 0 | `/setup-matt-pocock-skills` | Разовая настройка репозитория: где issues, какие лейблы, где хранить CONTEXT.md/ADR |
| 1 | `/grill-with-docs` | Допрос по фиче раундами вопросов, попутно строит словарь терминов (CONTEXT.md) и ADR |
| 2 | `/prototype` (опционально) | Когда вопрос нельзя решить словами — одноразовый прототип (HTML-файл или несколько UI-вариантов на одном роуте) |
| 3 | `/to-spec` | Синтезирует уже обсуждённое в спеку — без новых вопросов |
| 4 | `/to-tickets` | Режет спеку на тикеты-«вертикальные срезы», каждый с указанием, чем заблокирован |
| 5 | `/implement` | Реализует один тикет: внутри гоняет `/tdd`, в конце — `/code-review`, коммитит |
| 6 | `/tdd` (внутри implement) | Red-green-refactor по одному тесту за раз, на заранее согласованных «швах» |
| 7 | `/code-review` (внутри implement) | Два независимых сабагента: Standards (стандарты + смёллы Фаулера) и Spec (соответствие тикету) |

### Точки входа (откуда берётся работа)

- **`/triage`** — разбор входящих багов/просьб со стороны (не тех, что вы сами придумали). Проверяет, не сделано ли уже, пробует воспроизвести баг, при нужде допрашивает, публикует agent-ready бриф.
- **`/diagnosing-bugs`** — для сложных багов: сначала строится «тугая» команда, которая гарантированно падает на баге, только потом выдвигаются гипотезы (3–5, ранжированные).
- **`/wayfinder`** — для больших туманных эффортов (гринфилд-проект, огромная фича). Строит «карту» из тикетов-решений, работает по одному тикету за сессию (см. раздел 3 ниже).

### Здоровье кодовой базы

- **`/improve-codebase-architecture`** — сканирует код (упор на «горячие» недавно менявшиеся места), выдаёт HTML-отчёт с кандидатами на переделку.

### Словарь под капотом

- **`/domain-modeling`** — ведение словаря терминов проекта (CONTEXT.md), ADR только когда решение трудно отменить + неочевидно + был реальный выбор.
- **`/codebase-design`** — словарь для архитектуры кода (Module/Interface/Depth/Seam и т.д.) — **не про визуальный дизайн**, несмотря на похожее название.

### Остальные полезные

- **`/handoff`** — сжать разговор в файл для новой сессии/коллеги.
- **`/wizard`** — генерирует bash-скрипт-мастер для шагов, которые может сделать только человек (завести сервер, подключить сервис и т.п.).
- **`/wait-what`** — «не долетело» — переспросить агента проще.
- **`/teach`** — обучение самого себя новой теме за несколько сессий.

## 2. Полный алгоритм для новичка — с нуля до MVP

**Пример: клон Инстаграма.**

### Шаг 0 — то, что скиллы Покока не делают за вас
1. Создать папку проекта, открыть в Claude Code.
2. Своими словами (без скиллов) попросить агента создать стартовый проект — стек, база данных, загрузка картинок.
3. `git init`, первый коммит.

### Шаг 1 — разовая настройка
`/setup-matt-pocock-skills` → на вопрос про трекер задач для новичка выбрать **«локальные markdown-файлы»** (`.scratch/`), остальное — по умолчанию.

### Шаг 2 — не «весь Инстаграм», а список маленьких фич
Например по порядку: регистрация/вход → профиль → загрузка поста → лента → лайки → комментарии → подписки.
Каждый пункт — это отдельный проход по циклу ниже.

### Шаги 3–7 — цикл на ОДНУ фичу (повторять для каждой)
1. `/grill-with-docs` → передать идею фичи одной фразой → отвечать на раунды вопросов.
2. Если всплывает «как это должно выглядеть» — `/prototype` → передать конкретный визуальный вопрос → получить HTML с вариантами → выбрать.
3. `/to-spec` — ничего передавать не нужно, работает от разговора.
4. `/to-tickets` — режет спеку на тикеты, подтвердить список.
5. `/implement` — по одному тикету за раз, каждый в новой сессии/после `/clear`.

## 3. Как работать дальше — после того как MVP готов

Три источника новой работы:

### Сценарий A — сами придумали новую фичу
Тот же цикл: `/grill-with-docs` → `/to-spec` → `/to-tickets` → `/implement`.

### Сценарий B — баг/просьба со стороны (тестировщик, пользователь)
1. `/triage` → передать описание жалобы → получить решение (готово для агента / нужно уточнение / уже реализовано).
2. Дальше — `/to-tickets` → `/implement` как обычно.

### Сценарий C — большая мутная область (например, добавить личные сообщения)
`/wayfinder` вместо `/grill-with-docs` (подробности в разделе 4).

### Фоновая гигиена (не привязано к конкретной фиче)
`/improve-codebase-architecture` — раз в 1–2 недели, чтобы код не превращался в кашу.

**Шпаргалка выбора:**

| Откуда задача | С чего начать |
|---|---|
| Придумали сами | `/grill-with-docs` |
| Баг/просьба со стороны | `/triage` |
| Большая мутная область | `/wayfinder` |
| Код стал грязным | `/improve-codebase-architecture` |

## 4. Как на практике работает `/wayfinder` (несколько сессий)

`/wayfinder` не заменяет допрос — он растягивает его на много маленьких сессий вместо одного разговора.

1. **Первый запуск**: `/wayfinder` → передать мутную идею → получить путь к «карте» (файл, например `.scratch/личные-сообщения/map.md`).
2. **Каждый следующий раз**: новая сессия (новое окно или `/clear`) → `/wayfinder` → передать путь к этой же карте → агент сам берёт следующий нерешённый вопрос (или вы указываете, какой) и решает **только его один**.
3. Повторять шаг 2, пока карта не закроется полностью.
4. Правило: **одна сессия = один вопрос** — чтобы решения не путались контекстом друг друга. Раз в сессии — не считая research-тикетов, которые можно решать параллельно фоновыми агентами.

### Что делать, когда «туман рассеялся»
Возврат в обычный цикл:
```
/to-spec  (передать путь к закрытой карте) → /to-tickets → /implement по тикету
```
**Не перескакивать** сразу с карты в `/implement`, минуя `/to-spec` — иначе теряется связь между решениями с разных сессий.

### Как не запутаться между старыми и новыми тикетами при повторном большом апгрейде
- Готовые тикеты **закрываются** — никогда не попадают в список текущих задач.
- Каждый большой апгрейд (через `/to-tickets`) физически лежит в **своей отдельной папке** (`.scratch/<название-фичи>/issues/`) — второй апгрейд не пересекается с первым структурно.
- Каждая карта `/wayfinder` — тоже отдельная, со своими дочерними тикетами.
- Правило: не начинать вторую большую карту, пока по первой не закрыты (или явно не отложены) все тикеты.

### Что если не закончил старые фичи и начал новые
Это нормально и предусмотрено — каждый тикет самодостаточен (файл содержит всё нужное: что строить + критерии приёмки), не требует памяти о разговоре, в котором его придумали.
- Можно спросить агента: «загляни в `.scratch/` и скажи, какие фичи не доделаны».
- Взять нужный файл тикета → `/implement` — как будто только что нарезали.
- Если тикеты зависели друг от друга — продолжать с того, у которого блокеры уже закрыты.
- Система сама не напомнит о забытом — периодически стоит просить агента проверить `.scratch/` вручную.

## 5. Дизайн — как не получить «ИИ-помойку» по внешнему виду

**Честно:** скиллы Покока эту проблему системно не решают — это инженерный процесс, не дизайн-система. Единственный рычаг у Покока — `/prototype`, и то только для одного конкретного экрана за раз (несколько вариантов, переключаемых в браузере).

**Решение — уже установленный отдельно скилл `impeccable`:**

| Команда | Что делает |
|---|---|
| `/impeccable init` | Зафиксировать продукт и стиль → создаёт `DESIGN.md` |
| `/impeccable shape` | Спланировать UX экрана до написания кода |
| `/impeccable critique` / `audit` | Оценить готовый экран (иерархия, доступность, адаптивность) |
| `/impeccable polish` / `bolder` / `quieter` | Довести экран до товарного вида / добавить или приглушить яркость |
| `/impeccable extract` | Собрать единую дизайн-систему из уже написанного кода |

*(Не путать `/codebase-design` Покока с дизайном экранов — это про архитектуру кода, не про визуал.)*

### Совмещённый алгоритм — точные вызовы

**Один раз в начале проекта:**
1. `/impeccable init` → передать описание продукта и стиль → получить `DESIGN.md`.
2. `/setup-matt-pocock-skills` → как в разделе 2.

**Сценарий A (обычная фича):**
1. `/grill-with-docs` → передать идею → отвечать на вопросы.
2. При визуальном вопросе → `/prototype` → передать вопрос → получить HTML с вариантами.
3. Выбрать вариант → `/impeccable critique` → передать путь к варианту → получить замечания.
4. При необходимости → `/impeccable polish` → передать файл + замечания → получить доработку.
5. Вернуться в `/grill-with-docs` → сообщить выбранный вариант → продолжить допрос.
6. `/to-spec` → `/to-tickets` → `/implement` по тикету, как обычно.
7. После постройки экрана → `/impeccable audit` → передать путь/роут экрана → получить отчёт → при замечаниях — новый маленький тикет.

**Сценарий B (баг/просьба):**
1. `/triage` → передать жалобу.
2. Если жалоба про визуал → `/impeccable audit` → передать путь к экрану → получить список недочётов → приложить к брифу triage.
3. `/to-tickets` → `/implement` → `/impeccable audit` на результат.

**Сценарий C (`/wayfinder`):**
1. `/wayfinder` → передать идею → получить путь к карте.
2. На вопросах про внешний вид — `/prototype` + `/impeccable critique` внутри той же сессии, ответ фиксируется в карте.
3. По закрытии карты → `/to-spec` (путь к карте) → `/to-tickets` → `/implement` → `/impeccable audit`.

**Фоновая гигиена:**
1. `/improve-codebase-architecture` — раз в 1–2 недели.
2. `/impeccable audit` на ключевые экраны — параллельно.
3. Если сильно разъехалось — `/impeccable extract` → обновляет `DESIGN.md`.

### Откуда брать «путь к экрану» / «путь к прототипу»
- **Прототип:** агент сам сообщает путь/ссылку в конце работы `/prototype` — просто скопировать из ответа.
- **Реальный построенный экран:** либо ссылка на живую страницу (`http://localhost:3000/feed`), либо путь к файлу компонента в коде (`src/app/feed/page.tsx`) — можно дать любое, агент поймёт. Если не знаете — просто попросить словами («сделай аудит экрана ленты»), агент найдёт сам.

## 6. Иконки и картинки

Ни Покок, ни `impeccable` картинки не генерируют — это не их задача.

- **Иконки** — генерация не нужна вообще. Берутся готовые бесплатные библиотеки (Lucide, Heroicons и т.п.) — агент просто подключает как обычный пакет. Желаемый стиль иконок можно один раз указать на `/impeccable init`.
- **Фото в постах** — по сути продукта это контент, который загружают сами пользователи, генерировать не нужно. Для тестовых заглушек — готовые сервисы вроде `picsum.photos` (просто ссылка).
- **Кастомные ИИ-картинки** (логотип, иллюстрации для пустых экранов) — единственный случай, где нужен отдельный инструмент. Claude Code сам не рисует. Алгоритм: сгенерировать вручную в другом сервисе (claude.ai, ChatGPT/DALL-E, Midjourney) → скачать файл → сказать агенту «вот файл, положи его сюда и используй» — это разовое ручное действие сбоку от основного цикла, не требует полного `/grill-with-docs → /to-spec`.

## 7. Автодеплой — чтобы видеть изменения онлайн сразу

**Не писать свой скрипт-мониторинг коммитов** — это уже решённая задача (называется CI/CD), своя реализация — лишняя сложность для новичка.

### Вариант 1 — управляемые сервисы (проще всего)
Vercel / Netlify / Railway / Render — подключаете GitHub-репозиторий один раз, дальше при каждом `git push` сами пересобирают и перезапускают, дают ссылку вида `проект.vercel.app`.

Алгоритм: `/wizard` → передать «хочу настроить автодеплой на Vercel при пуше в GitHub» → получить скрипт-мастер → пройти один раз.

**Важный нюанс:** деплой запускается **пушем**, а не просто коммитом — `/implement` по умолчанию только коммитит. Нужно либо каждый раз просить «запуш это», либо один раз попросить агента всегда пушить после коммита в `/implement`.

### Вариант 2 — свой сервер (self-hosted)
Если нужно именно на своём железе:
- **Простой способ:** git `post-receive hook` — при пуше на свой сервер мгновенно (не поллингом!) срабатывает скрипт пересборки.
- **Рекомендуемый способ:** готовая панель **Coolify** (аналоги — CapRover, Dokku) — превращает свой VPS в «свой личный Vercel»: подключаете GitHub через веб-панель, дальше всё само, включая бесплатный SSL.

Алгоритм: если нет VPS — `/wizard` → передать «хочу арендовать VPS у [провайдер]» → пройти скрипт. Затем `/wizard` ещё раз → передать «хочу поставить Coolify на сервер [IP] и подключить GitHub» → пройти скрипт.

Разница с Вариантом 1: тут сами отвечаете за сервер (обновления, безопасность), зато данные и инфраструктура — полностью свои.

## 8. Большой мультиплатформенный проект (моб + веб, разные аудитории)

Пример: мобильное приложение для пользователей, мобильное для рекламодателей, веб для пользователей, веб для рекламодателей.

### Структура кода — монорепозиторий
```
/apps
  /mobile-user
  /mobile-advertiser
  /web-user
  /web-advertiser
/packages
  /shared        ← общий код: API-клиент, общие компоненты
```

### Как это учитывают скиллы Покока
«Multi-context» — вместо одного `CONTEXT.md` на весь проект: главный `CONTEXT-MAP.md` + свой `CONTEXT.md` у каждой крупной части. `/setup-matt-pocock-skills` сам предложит такую раскладку, увидев признаки монорепозитория (структуру папок).

### Как это учитывает `impeccable`
Концепция **«surface» (поверхность)** — общий `PRODUCT.md`/`DESIGN.md` держит единый бренд, а у каждой части — свой «surface brief» с собственным режимом (например, «Operate» для рабочего инструмента рекламодателя, «Persuade» для вовлекающей ленты пользователя).

### Алгоритм
1. **Один раз в начале** — `/wayfinder` → передать: «спроектировать 4 части продукта, что общее, что разное, какой стек для мобильных» → получить архитектурные решения по карте.
2. Дальше — тот же цикл (`/grill-with-docs → /to-spec → /to-tickets → /implement`), только на `/grill-with-docs` агент дополнительно уточняет, для какой именно части фича.

### Как проверять внешне
- **Веб-части** — у каждой своя ссылка (`app.сайт.com`, `ads.сайт.com`), автодеплой как в разделе 7.
- **Мобильные части** — браузером не открыть. Сервис **Expo** (для React Native) даёт мгновенный просмотр текущей версии на своём телефоне через QR-код, без публикации в магазины. Настраивается через `/wizard`. Полноценная публикация в App Store/Google Play (TestFlight, внутреннее тестирование) — отдельный, более поздний шаг, нужен только для тестировщиков со стороны.
